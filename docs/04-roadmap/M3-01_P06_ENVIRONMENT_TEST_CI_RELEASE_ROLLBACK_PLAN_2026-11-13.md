## 1. Purpose and non-goals

Define the environment boundaries, deterministic quality gates, CI expectations, release controls and recovery strategy for the first bounded V2 foundation package.

This is a planning document only. It does not install packages, create environments, provision databases, change Hostinger settings, create DNS/subdomains, deploy, run migrations, access V1 or process real data.

## 2. Environment model

| Environment | Purpose | Data | Secrets / access | Current status |
|---|---|---|---|---|
| Developer workstation | Local development and debugging | Fabricated synthetic fixtures only | Local-only development secrets; never production credentials | Conceptual; not activated |
| GitHub CI | Reproducible build, static checks and automated tests | Synthetic fixtures generated by tests | No production/Hostinger secrets; least-privilege repository token only if required | Existing repository documentation workflow only; application CI not yet built |
| Optional preview | Later review of a candidate build | Synthetic fixtures only | Separate short-lived preview secrets; no V1 access | Not approved or provisioned |

Do not create a staging environment if it requires new spending or changes to V1. A local + GitHub CI-only foundation is sufficient for the first package.

## 3. Runtime and dependency policy

- Target Laravel 13 and PHP 8.5, subject to a read-only V2 compatibility check before implementation.
- If the actual V2 runtime cannot satisfy Laravel 13 requirements, stop and return to the Product Owner. Do not silently downgrade to Laravel 12 or change database/framework family.
- Use Composer 2 with a committed dependency lockfile; package installation is allowed only after a separate implementation authorization.
- Use only maintained, supported dependencies with documented purpose and license. Avoid unnecessary packages.
- Do not add Redis, persistent workers, external search engines, vector stores, container infrastructure or AI SDKs in the initial foundation.
- Keep secrets in environment-specific secret storage; commit only a redacted example configuration. Never put secrets in GitHub, logs, test fixtures or chat.
- Re-check official lifecycle/security support at implementation time; this document does not freeze transitive package versions.

## 4. CI pipeline — required design

The first authorized foundation package should implement a deterministic GitHub Actions workflow with these ordered gates:

1. **Checkout and runtime:** pin supported action versions and configure the approved PHP runtime.
2. **Dependency integrity:** install from the lockfile in CI only; do not update dependencies implicitly.
3. **Static quality:** formatting/lint and framework configuration validation.
4. **Security hygiene:** secret scanning, dependency advisory review and checks for unsupported/outdated dependencies.
5. **Unit tests:** domain rules, validation and policy functions using synthetic fixtures.
6. **Feature/smoke tests:** public health route, safe error handling, anonymous access and no accidental privileged route exposure.
7. **Privacy/visibility tests:** Deeni Madaris default-OFF non-exposure across every implemented public surface, including direct IDs and query variations.
8. **Artifact/build check:** verify reproducible build and ensure environment files, credentials, logs and private test artifacts are not included.
9. **Documentation/link checks:** required project documents and local references validate.

No CI job may connect to Hostinger, V1, production databases, external source systems, model providers or paid APIs. CI must not deploy or run database migrations.

Tests must be added before corresponding features. If a surface does not yet exist, record it as a future required test; do not claim it has passed.

## 6. Branch, review and merge policy

- Continue documentation-first and protected-PR workflow.
- Every implementation task must have a narrow issue/acceptance statement and a dedicated branch/PR.
- No direct pushes to main for application changes.
- Require the project’s documented CI checks to pass on the exact PR head.
- Review the complete diff for accidental secrets, V1 references/data, scope expansion and unapproved dependencies.
- Use small reversible changes; merge only after checks and owner review.
- No automatic merge for changes affecting privacy, publication eligibility, source rights, identity, security policy or Deeni Madaris suppression.
- The Product Owner remains the final decision-maker; ChatGPT is not an independent security approver.

## 7. Release and rollback design

The first foundation package ends at a reproducible local/CI artifact and documentation. It does not deploy to Hostinger.

If a later separately authorized deployment is considered, it must have a separate release record containing:
- Exact V2 target path/document root and proof V1 routing/files are unaffected.
- Exact artifact/commit and dependency lock hash.
- V2-only configuration and least-privilege database identity.
- Approved backup of V2-owned state and verified restore path.
- Pre-release smoke tests and post-release verification.
- Named human release approver and operator.
- Explicit stop conditions, rollback command/runbook and recovery owner.
- No schema migration unless separately reviewed and explicitly authorized.
- No DNS, PHP-global setting, V1 file, V1 database or shared production configuration change.

Rollback must restore the previous V2 artifact/configuration only. If rollback could affect V1 or shared settings, stop; do not proceed.

## 8. Backup, recovery and data handling

For the synthetic-only foundation, preserve source control and reproducible fixtures; no live database backup is needed because no live V2 database is authorized.

Before any later V2 data-bearing pilot:
- Define V2-specific backup ownership, encryption, access, retention and deletion.
- Confirm whether the Hostinger weekly backup includes the selected V2 path and separate database; do not assume it does.
- Establish an independent export of V2-owned data in a portable format if permitted by the plan.
- Perform a restore rehearsal into an isolated V2-only target using synthetic data.
- Record measured RPO/RTO and compare against owner-approved objectives.
- Verify that restore does not overwrite or expose V1.
- Treat backup failure or unverified restore as a release blocker.

## 9. Severity and stop conditions

**Critical — stop immediately:** suspected V1 access/change; secret exposure; public private-file exposure; suppressed-category leakage; real personal data in fixtures/logs; unauthorized source collection; unexpected external network/API activity; unapproved spend; production write/migration; or cross-tenant V1/V2 access.

**High — block merge/release:** failing security/visibility tests; unsupported runtime/dependency; missing rollback plan; unreviewed high-impact policy change; CI using privileged or production credentials; unbounded background task.

**Medium — fix before feature completion:** reproducibility, accessibility, performance, documentation or observability defects that do not create an immediate exposure but undermine acceptance.

On any Critical condition: stop the workflow, do not retry with broader permissions, preserve minimal diagnostic evidence without secrets/personal data, and ask the Product Owner for a decision. No automatic remediation or production operation.
